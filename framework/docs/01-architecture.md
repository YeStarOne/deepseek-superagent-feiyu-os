# 01 · 架构：四层

> 一句话：**聊天直连，事件工单；感知先过滤，观察先于自动；开发靠信箱，推进靠班次。**

## 1. 四层

```
┌─ L3 项目记忆 ─────────────────────────────────────────────┐
│  AGENTS.md · HANDOFF.md · 滚动计划表 · 决策日志 · PR 制      │
├─ L2 班次 ─────────────────────────────────────────────────┤
│  心跳调度 · 定向唤醒 · 看护（停滞/中断）· 收工交接            │
├─ L1 信箱投递 ─────────────────────────────────────────────┤
│  cli 轮询 · hook 回合边界注入 · wake 空闲唤起                │
├─ L0 传输与身份 ───────────────────────────────────────────┤
│  团队 · 地址 person/session · relay · 会话类型               │
└──────────────────────────────────────────────────────────┘
```

- **L0 不自研**：用现成的 Reason Network（MIT / Apache-2.0），自建一个 relay 即可（一台云主机 + tailnet，零 DNS）。
- **L1 是唯一的公共面**：所有 harness 都能实现"读文件 → 注入 → 回信"。
- **L2 让系统在人不在时继续走**。
- **L3 是记忆**：不在上下文里，在仓里。

## 2. 三种投递，同一份语义

| 适配器 | 适用对象 | 机制 | 代价 |
| --- | --- | --- | --- |
| `cli` 轮询 | 没有 harness 的成员（桌面助手、只会读写文件的模型） | 常驻进程长轮询团队信箱，写 `inbox.md`；监视 `outbox.md` 发送 | 不是实时；要人把文件喂给它 |
| `hook` 注入 | harness 活着、正在跑 | 在回合边界（会话开始 / 工具调用 / 回合结束）把新消息注入上下文 | 会话结束就失效 |
| `wake` 唤起 | harness 活着、但会话睡着了 | 用**宿主自己的调度器**插一条一次性运行，让会话醒来读信 | 有 20–30 秒延迟；要节流 |

**铁律：唤醒通道只放一句固定话术，消息正文永远走 hook。**
这样即使调度器被第三方看到，也看不到任何消息内容。

## 3. 唤醒是怎么做到的

会话睡着时，hook 不会触发，消息就一直躺着——多 agent 团队死在这里。

做法不是注入进程，而是借宿主的自动化调度器：

1. 给每个会话准备一条**永不自动触发**的辅助自动化（cron 写 2 月 29 日，只用来承载一次性运行）；
2. 消息到达且会话空闲 → 插一条 `manual` 运行；
3. 宿主在约 20 秒内认领、恢复会话、喂一句固定话术；
4. 消息本身通过正常 hook 进入这一回合的上下文。

四条安全轨：

- **忙的会话不打断**：回合中收到消息走正常 hook，不插唤醒；
- **按会话节流**（默认 120 秒，下限 5 秒）：一串消息只醒一次；
- **单飞**：已有唤醒在跑就不再排队；
- **模型线回退**：唤醒跑在"已知可用"的模型线上；上次失败则换备用线，避免把人叫醒到一个没额度的模型上。

## 4. 事件线（产品运行时）

```
Source ──Trigger──▶ 准入闸（确定性） ──▶ 研判（模型） ──▶ 工单 ──▶ worker
                                                                  │
                             ready / waiting / blocked / failed ◀─┘
                                        │
                                   出海通道（限速、幂等、免打扰）
```

- **准入闸是确定性的**：人 / 机器人 / 名单 / 范围，先过表，再谈判断。
- **研判必须给证据**：方向明确 + 至少命中一条规则 + 意图证据；缺一条就不接。
- **`observe` 只记录 `would_accept`，不真开单**：这是"观察先于自动"的落点。
- **切闸留痕**：`policyVersion` + 切闸时刻落盘，可回滚（见 feiyu/ 案例二）。

## 5. 两条线不混

- **聊天线**：人在说话，要秒回。不进制裁、不进工单，避免 30 秒级的研判拖慢对话。
- **事件线**：机器事件，要判断。可以慢，但必须可追溯、可拒绝、可回滚。

判据只有三个：**实时性**（要不要立刻回话）、**时长**（会不会挡住聊天）、**来源**（人还是机器）。

## 6. 适配器契约（五个原语）

任何 harness 想接进来，实现这五个就够：

| 原语 | 要求 |
| --- | --- |
| `identity` | 会话键 ↔ 团队地址映射；重启后要能重新寻址（旧键会退化成进程号） |
| `inject` | 回合边界把消息注入上下文；重复投递要幂等 |
| `wake` | 空闲唤起；必须节流、单飞、忙时不打断、失败可回退 |
| `send` | 回复带幂等键；失败退避；永久失败要落盘 |
| `presence` | 上报在做什么（doing），让团队看得见 |

## 7. 工程哲学（从事故里长出来的）

- **失败闭合**：闸门不确定就关门，并开 issue；不允许"大概没问题"。
- **校验落在被消费的那一份上**：源文件对了不算，进程里跑的、目标机上落盘的才算。
- **比例必须有分母**：`n=0` 不算通过；"100%" 必须说清样本量。
- **信号与守门分开**：两边都绿的断言没有鉴别力，不能拿来证明切换成功。
- **每轮一句话日志**：人醒来只看结论与证据链接，不追聊天记录。
