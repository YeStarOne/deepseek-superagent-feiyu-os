# 案例四 · 动作没生效，日志里却没有 error

## 问题

部署脚本输出成功，服务重启完成，日志干净——线上行为还是旧的。

## 三个真实成因

1. **包管理器覆盖了运行时副本**
   `pnpm install` 会用源目录覆盖 profile 下的副本，并顺手吞掉**只存在于副本里的补丁文件**（源目录里没有，所以覆盖后就没了）。
   结果：补丁消失、功能静默降级，日志只在启动时有一行无害的警告。

2. **换行符炸掉了管道**
   文件里混进 CRLF，`set -euo pipefail` 让整条管道失败；但 `bash -n`（只查语法）**抓不到**，脚本语法完全合法。
   结果：脚本"成功"，实际没执行到关键分支。

3. **哈希对账方式错了**
   只验证"文件能解开 / 是合法文件"，没验证**两边相同**。传输截断后的文件仍然是"合法"的。
   结果：传了一半的脚本被执行。

## 做法：三关全在目标机侧验

1. **`sha256` 相同**——不是"能解压"、不是"大小差不多"，是哈希逐位相同；
2. **字节检查**——`grep -c $'\r'` 必须为 0（在消费侧检查，不是源侧）；
3. **语法检查**——`bash -n` / `python -m py_compile`（注意它抓不到 CRLF，所以必须排在第二关之后）。

再补一条：**消费侧再 grep 一次关键字节**，确认落盘的就是要跑的那一份。

## 结果

- 同类故障不再复发；
- 每次部署都能给出三关输出，而不是"应该好了"。

## 为什么这条值得公开

这不是本项目独有的坑。
上游 hot-installer 的 CHANGELOG 里能查到三例同族问题——它们都不是"代码写错了"，而是**"改的东西没有被真正消费"**。

## 一句话

> **校验必须落在被消费的那一份上。**
> 源文件对、仓库对、甚至目标目录对，都不算；跑起来的、落盘的、实际被读的那一份对，才算。
