# 案例一 · 9.5 小时夜班自主持

**时间**：2026-11-06 23:00 → 2026-11-07 08:30
**角色**：总架构 chief（唯一合并权）+ 看护脚本

## 问题

人睡了，项目就停。
多个会话并行改同一个仓，谁先合并、谁被打回、谁在等谁——全靠人记，一觉醒来就是冲突和一堆分叉。

## 做法

1. **一条心跳**：20 分钟唤醒 chief。不是每个角色一条定时任务。
2. **每轮四件事**：查信箱 → 巡检生产（服务状态、日志、指标）→ 合并开放 PR → 更新滚动计划。
3. **看护脚本**：扫"error / interrupted 且 todo 里有 in_progress"的会话，定向唤醒；忙的会话不打断。
4. **合并权唯一**：chief 是唯一能写 `main` 的人；其他会话只开 PR。
5. **每轮一句话日志**：做了什么，或者"巡检正常 + 具体数值"。

## 结果

- **33 个 PR 合并**，另有 1 个被更新的实现取代而关闭（#25）；
- **52 个 `main` 提交**；
- **0 冲突遗留**，`main` 保持线性；
- 第二天早上人只看交接文档与滚动计划，不追聊天记录。

## 证据

实现仓 `docs/history/2026-11-07-夜班主持.md`（私有仓）与滚动计划表的状态变更记录。

## 可复用点

- 心跳只有一个人，合并权只有一个人，其余全部 pull 档。
- 夜班不追求"做得多"，追求"每一步都有证据、都能回滚"。
- 交接文档是第二天的唯一入口；没有交接的轮次视为没做完。

## 反例（我们踩过的）

- 早期给多个角色各挂一条 cron：同秒唤醒，在并发上限上互掐，谁都跑不完。
- 用"我改完了"当交接：下一轮的人要重读全部上下文，等于没交接。
