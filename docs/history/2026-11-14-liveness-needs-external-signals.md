# 工程史 · 判活只认外部真信号

> 一句话：**"活着"不是本地属性，是能从外部观察到的事实。** 心跳、端口、状态文件、探活端点都可能撒谎或残留；判活必须用消费者视角、穿过整条链路的真信号。
> 与 [2026-11-07 断言落在被消费的那份上](2026-11-07-assert-on-the-consumed-copy.md) 同族：那次是"验错了对象"，这次是"验活的信号本身会撒谎"。

## 1. 为什么单独立一条

同类事故的共同签名是：**判活信号全绿、真实链路全死**——或者反过来，全红、其实活着，把活进程误杀。
看护/巡检的每一个信号都值得过一遍审讯：它写在什么时机？死掉后会不会残留？是从谁的视角看的？

## 2. 已知五种变体

| 变体 | 信号说 | 实际 | 怎么抓 |
| --- | --- | --- | --- |
| 心跳日志 | 每轮照打 | 每轮抛异常被 `catch {}` 吞 | 日志 mtime（停写=假活）+ 重启段异常计数必须 0 |
| 名字子串 | "老成员进程在" | 新成员被误认、被顶掉 | 双向对照：A 在跑时用 B 的名字查，必须为空；匹配用词边界正则 |
| 端口 LISTEN | "服务在" | 客户端已死、对端监听残留（NAT 假活） | 穿链路发真请求，超时即尸体；杀掉让守卫重拨 |
| 探活端点 200 | "网关健康" | 真实请求成片挂死 | 探针发真补全：`max_tokens ≥ 8`、只认 `completion_tokens > 0` |
| 状态文件 ok | "它认为进程在" | 杀后仍在写旧 PID | 杀完当场核进程表为空；状态由动作后的重新探测写入 |

## 3. 本仓已落地的对应措施

- **判活三铁律**：不子串匹配（加新成员先列一遍所有按名字判活的地方）；心跳日志 ≠ 存活判据（判忙锚"开始/进行中"的行，异常计数必须 0）；活不认端口认外部真信号（判据 =「距最后一次可观测事件 < N 秒」）。完整叙事见[案例五](../../feiyu/docs/03-cases/05-false-alive.md)。
- **收尸闭环**：外部探针 → 探死即杀 → 守卫自动重拨，不依赖人半夜手工上线；闭环必须真演练过（全杀 → 纯等定时任务 → 秒级自愈）才算上线。
- **探针设计**：`max_tokens ≥ 8`、只认 `completion_tokens > 0`、探针流量与真实流量分开统计不进延迟分位。
- **杀进程的收尾**：杀完当场确认死透（进程表为空），再让下一个动作接管；"它认为在"和"真的在"分开记账。

## 4. 写新看护脚本时的自查三问

1. 这个信号会撒谎吗？（写时机在动作之前？在异常之前？在别的进程的脑子里？）
2. 这个信号死掉后会残留吗？（端口、锁文件、状态文件——尸体最擅长假装活着。）
3. 这个信号是从消费者视角看的吗？（穿整条链路发真请求，还是只看本地一跳？）
