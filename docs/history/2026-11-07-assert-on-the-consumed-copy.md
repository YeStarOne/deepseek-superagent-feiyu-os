# 工程史 · 断言必须落在被消费的那一份上

> 一句话：**你校验的东西，必须是运行时真正读的那一份。** 校验了"上游原件"或"看起来等价的东西"，通过与否都不代表运行时是对的。
> 这是本仓踩得最多的一类坑，写法统一记在这里，新脚本/新部署先对照一遍。

## 1. 为什么单独立一条

同类事故的共同签名是：**日志全绿、验收通过、功能全哑**。
因为验收点选在了一个"被消费的副本之外"的位置——模板文件、源码目录、安装包的中间产物、跑得通但不代表被采纳的闸门。

[案例四](../../feiyu/docs/03-cases/04-deploy-silent-failure.md) 是这个家族的完整叙事；本节只列可复用的对照表。

## 2. 已知六种变体

| 变体 | 你验的 | 真正被消费的 | 怎么被抓出来 |
| --- | --- | --- | --- |
| 模板 vs 成品 | 模板里占位符填得对 | 渲染后写进 systemd/cron 的那一串 | 在**渲染后的字符串**上断言残留占位符 |
| 源码 vs 构建产物 | `src/` 逻辑正确 | 进程加载的 `lib/` 或 wheel 里的副本 | 断言落在产物上，并校验产物比源码新 |
| 语法 vs 行尾 | `bash -n` 通过 | 服务器上那份带 CRLF 的文件 | `grep -c $'\r'` 在**目标机**上查，或查 git blob（`git ls-files --eol`） |
| 传输 vs 完整 | `scp` 返回 0 | 远端落盘那份 | 两端 sha256 相同才算送达（"合法"≠"相同"） |
| 准入 vs 执行 | `would_accept` 记录 | 真的开单、真的派发 | 切闸后看 `kind` / `ticketId` 是否翻转，而不是只看准入 |
| 空集 vs 通过 | 比例 100% | 分母是 0 | 任何比例判据先断言分母 > 0 |

## 3. 本仓已落地的对应措施

- **部署三关**：sha256（防截断）→ 行尾（防 CRLF）→ 语法（`bash -n`），三关**全部在服务器侧**执行。见 [feiyu/docs/05-runbook.md](../../feiyu/docs/05-runbook.md) 与 [docs/06-sanitize.md](../06-sanitize.md)。
- **安装脚本的装前断言**：不在模板文件上查残留 `@[A-Z_]+@`，而在**渲染后的成品**上查，命中即 `exit 5`，不把空值带进 systemd/cron。见 [install/README.md](../../install/README.md) 的契约段。
- **占位符按消费者分**：机器消费者（systemd / cron）用惰性 `@X@`（缺填一眼可见）；人读文档与 cordis 补丁层用 `${X}`。理由见 [feiyu/docs/04-deploy.md](../../feiyu/docs/04-deploy.md) 的"两种占位符，两个消费者"。
- **比例判据带分母守卫**：`n == 0` 不算通过。见 [framework/docs/01-architecture.md](../../framework/docs/01-architecture.md) 的工程哲学。

## 4. 写新脚本时的自查三问

1. 我这条 `--verify` 读的，和用户/进程真正读的，是同一个路径吗？
2. 这份文件在**目标环境**（不是我的机器、不是 git 工作树）里长什么样？
3. 如果这条断言错了，是"假绿"还是"假红"？假绿更贵——它会挡住后面所有人的排查。
