# 工程史 · 停机窗只装得下确定性

> 一句话：**停机窗里只允许「本地、原子、必然成功」的动作；一切需要网络、可能失败、可能重试的事，都必须在窗前完成并验完。**
> 与 [判活只认外部真信号](2026-11-14-liveness-needs-external-signals.md) 同族：那次讲"验收信号不能撒谎"，这次讲"窗内动作不能赌"。

## 1. 为什么单独立一条

升级窗的风险从来不是步骤多，是**窗内有不可控因素**。传统做法（停服 → npm install → 起服务）把最可能失败的一步放在风险最大的时刻：服务已停、回滚面最大、网络不受控。把所有可失败动作移到窗前，停机窗就从"祈祷"变成"机械执行"——本次实测 27 秒。

## 2. 窗内动作合法性对照表

| 动作类型 | 窗内合法 | 理由 |
| --- | --- | --- |
| mv / cp（同盘、源已验证） | ✓ | 原子、本地、秒级 |
| sed 改配置（窗前已备份原文件） | ✓ | 全窗唯一非原子步，所以必须窗前备份 |
| daemon-reload + start | ✓ | 本地、确定性 |
| npm install / git clone | ✗ | 网络、可重试、失败即卡窗 |
| 首次真启动验证 | ✗ | 结果未知 ⇒ 隔离环境窗前先跑 |
| 数据合入 / 迁移 | ✗ | 与升级同窗 = 永远无法归因 |

## 3. 本仓已落地的对应措施

- 升级 runbook 两段式模板：**P-prep（白天不停服：装树 + 验证 + 回滚料预置）** / **夜窗（纯本地原子动作）**；前置 Gate 清单每条带实证。
- 正对照三件套：同副本双核配置对比 / 关调试前的写入计数 / 无关任务的正常节奏。
- 隔离真启动测试：隔离 HOME + 默认模板 + 堆帽，9 秒监听定案 engines 是建议值。
- 回滚料离线预置，**回滚本身也要验收**。
- 自愈看护在场 ⇒ 手工让位（别抢）。

## 4. 升级前自查三问

1. 窗内还有会失败的动作吗？（任何网络步骤 ⇒ 移到窗前）
2. 每条验收有对照组吗？（0 ≠ 没写过；既有告警 ≠ 新增告警；探针 ≠ 生产流量）
3. 回滚料离线可用吗？（回滚窗里不该出现任何"第一次"）
