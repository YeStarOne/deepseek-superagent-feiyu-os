# 案例六 · 两段式升级：27 秒停机窗，窗里只装得下确定性

## 问题

一次正式升级（核心 0.2.1-rc.2 → 0.2.2-rc.3，配套自动化插件 1.0.13 → 1.0.27）。传统做法把 `npm install` 留在停机窗里做——网络一抖，就卡在风险最大的时刻：服务已经停了，回滚面最大。另一个更隐蔽的诱惑是把升级和数据合入塞进同一个窗口：出事连归因都做不到。

## 做法：白天把一切"会失败"的事做完验完，夜窗只做本地原子动作

**白天（不停服）清单，每条带实证：**

- **整棵依赖树装进独立临时前缀，且必须 `--install-strategy=nested`。** 生产形态是自足的嵌套目录（实测 1.3G / 214 包）。坑一：`npm install --prefix` 默认平铺，主包只剩几 MB 的空壳——停机窗里 mv 上去就是搬空壳，服务起不来。坑二：装完的体积要等 npm 完全退出再量（中途量 590M，终态 1.3G）。
- **配套插件单独前缀 + `--legacy-peer-deps`**：同前缀安装直接 ERESOLVE（91 个 peer 依赖在根项目没有宿主），解不开。
- **兼容性用正对照**：同一份 profile 副本，让新旧两个核心各 dump 一次配置，逐行比对。4 条 `patch: entry not found` 告警两核一模一样 ⇒ 既有状态，不是升级引入。没有对照组，既有告警会被当成升级的锅。
- **engines 是建议值，用隔离真启动定性**：声明 `>=24.9` 而宿主是 22——隔离 HOME + 默认模板真启动，9 秒监听 / 0 插件错误 / RSS 313MB（320MB 堆帽）⇒ 不为它升级运行时。
- **CLI breaking change 先在测试里撞出来**：`dsh web` 子命令被 0.2.2 拒绝（`too many arguments`）⇒ service 单元启动写法要改。这个改动留在窗内做，就是二次风险。
- **回滚料全部离线预置**：旧核心整目录改名留档（自足可回滚）、旧插件目录、service 备份。回滚窗里不出现任何"第一次"。

**夜窗（t0 → t1，只做本地原子动作）：**

stop → mv 旧核心为 `.bak` → mv 新核心 → mv 插件 → sed 改 service 启动参数 → daemon-reload → start。**27 秒。**

原则一句话：**mv 是原子的，网络不是。**

## 结果

27 秒停机、零回滚、验收全绿。真消息端到端（防抖 → 合并 → 回合完成）3 分钟内闭环；窗后 3 分钟，一个与升级无关的第三方定时任务（图片发布类）自行跑通——生产流量比探针硬。

## 验收的对照组（没有对照组的验收不算验收）

- 真消息端到端：防抖窗口开启 → 合并提交 → 回合完成，全程日志可核。
- 「调试分支确认真关」必须带正对照：以关调试前的写入计数（1001 / 299 行）为前提，"升级后仍为 0"才是证据——没有前置计数，0 只等于"从没写过"。
- 「既有告警 ≠ 新增告警」：dump-config 对比里两核同现的 4 条告警，不是升级的锅。
- 同窗两变更 = 永远无法归因：升级窗避开当天上午的数据合入窗；而记忆召回从当天合并后的主库实召回一张卡，一次覆盖两个变更——各自独立验收，互不污染。

## 看护让位

自愈型看护（单例锁 + 60 秒轮询）在场时，手工 restart 让位：手工那次输给了 PATH 环境，看护 60 秒内自己接管成功——不是故障，是设计在工作。升级者别抢看护的活。

## 教训

1. **停机窗的长度 ≈ 窗内"可能失败的动作"数量。** 把动作移出去，窗口自然短。
2. **每条验收都要有对照组**：0 ≠ 没写过；既有告警 ≠ 新增告警；探针 ≠ 生产流量。
3. **回滚的正确形态是"离线预置的确定性动作"**，不是"出事再想办法"。
