# 开发案例

四个案例都来自真实运行，数字可核。写法统一：**问题 → 做法 → 结果 → 证据 → 教训**。
不写"我们很努力"，只写"哪一步做错了、怎么发现的、现在怎么防"。

| # | 案例 | 一句话 |
| --- | --- | --- |
| 1 | [9.5 小时夜班自主持](01-night-shift.md) | 33 个 PR 合并、52 个提交、零冲突——心跳一个人，合并权一个人 |
| 2 | [观察先于自动](02-observe-before-auto.md) | 4/4 对账 → 100% 假阳性 → 收紧规则 → 切闸留痕可回滚 |
| 3 | [17 小时记忆断档](03-memory-gap.md) | 日志全绿、功能全哑：文件改对了不等于进程里跑对了 |
| 4 | [动作没生效但日志没有 error](04-deploy-silent-failure.md) | 部署三关：校验必须落在被消费的那一份上 |

## 为什么公开复盘

踩坑文档比成功故事有用。
社区里最常见的不是"不会写"，而是"改了但没生效、日志却没报错"——案例三和案例四是同一类：**你验证的对象，不是系统真正消费的对象。**
