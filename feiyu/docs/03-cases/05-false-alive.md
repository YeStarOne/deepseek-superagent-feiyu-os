# 案例五 · 看护判活五连败：她明明死了，看护说她还活着

## 问题

值夜班的看护层（替睡着的主角盯着生产系统的那一层）在一周里连续漏判五次——而且五个方向都有：该报的死没报，不该杀的活被杀，杀了之后的状态还在说谎。

「进程活着」从来不是看护能直接观测的东西，只能靠**信号**推断。这一周踩出来的，是五种信号各自撒谎的方式。

## 五个真实签名

### 1. 心跳说谎

看护循环每轮先写一行心跳日志再干活；干活时抛异常，被外层 `catch {}` 吞掉。
结果：心跳每轮照打、日志看着健康，**连续 15 轮实际全部作废**。
抓法：心跳不是判据。判活核两件事——日志的 mtime（进程在、日志停写，是假活的另一种形态）和**异常计数**（重启段逐行数异常，必须为 0）。

### 2. 名字相撞

按子串匹配进程名判活。新成员的名字里恰好含老成员的名字 → 新成员一启动就被当成"老成员还在"，两个互相拖死：老成员被顶掉，看护又永远认为"有人在"而不补位。
抓法：**双向对照**——新成员在跑时，用老成员的名字反查一遍，必须查不到；查到了就是相撞。
修：匹配用词边界正则（如 `(?<![-\w])名字\.ext`），不用裸子串。

### 3. 端口残留

连接的客户端死了，对端的监听进程还攥着端口不撒手（NAT 把半开的 TCP 维持成假活，传输层自己的收尸机制十几分钟都兜不回来）。
结果：端口照样 LISTEN，新连接一个个撞死在 bind 上，**整条链路全员陪葬**，而所有"看端口"的巡检都报绿。
抓法：**从另一端穿过去发真请求**。端口在不算活，穿链路的探活秒回才算活。
落地：外部定时收尸——探活超时即判尸体、杀掉、让守卫自动重拨。上线当晚僵尸监听的存活期从 **14 分钟+** 收敛到 **≤2 分钟**（收尸周期）。

### 4. healthz 假活

网关探活端点稳定回 200，真实请求却成片挂死。
根因：探针本身设计错了——`max_tokens=1` 的最小响应不经过真实生成路径，结构性测不出"整片停摆"。
修：探针必须发**真补全**：`max_tokens ≥ 8`、只认 `completion_tokens > 0`；探针流量与真实流量分开统计，不进延迟分位。

### 5. 状态文件说谎

看护把"认为进程在"写进状态盘；进程被杀后，状态文件还留着旧的 ok 和旧 PID，**第 31 轮仍在写**。
结果：所有读状态的工具都被骗过。
修：杀完**当场确认死透**（进程表为空才算），状态由动作之后的重新探测写入；"它认为在"和"真的在"是两个世界。

## 做法：判活三铁律 + 收尸闭环

1. **判活绝不子串匹配**——加新成员前，先把所有按名字判活的地方列一遍。
2. **心跳日志 ≠ 存活判据**——判忙锚"开始/进行中"的行，不是共同前缀；异常计数必须 0。
3. **活不认端口认外部真信号**——判据形式 =「距最后一次可观测事件 < N 秒」，从消费者那一端穿整条链路发真请求；本地单跳、状态文件、探活端点都只算旁证。

三条之上再盖一层：**收尸自动化**。外部探针 → 探死即杀 → 守卫自动重拨，闭环不再依赖人半夜手工上线。闭环做过真演练：全杀 → 什么都不做 → 纯等定时任务自己触发 → **25 秒**端口恢复、探活端点回 200（最坏延迟 = 收尸周期 + 重拨间隔）。

## 结果

- 五种签名进了工程史对照表（`docs/history/2026-11-14-liveness-needs-external-signals.md`），新看护脚本/新部署先对照一遍再上线。
- 之后同类报告的第一反应从「重启大法」变成「两端对照 + 外部真信号」，误杀与漏判都归零。

## 证据

数字与出处（私有仓）：

- 连续 15 轮作废 / 第 31 轮仍写 ok / 双向对照输出为空：看护迭代日志；
- 僵尸存活期 14 分钟+ → ≤2 分钟；自愈演练 25 秒：收尸任务上线与演练记录。

## 教训

「活着」不是进程的本地属性，是**能从外部观察到的事实**。写任何判活信号前先问三个问题：

1. 这个信号会撒谎吗？（写在抛异常之前？写在动作之前？写在另一个进程的脑子里？）
2. 这个信号死掉时会残留吗？（端口、状态文件、锁文件——尸体最擅长假装活着。）
3. 这个信号是从消费者视角看的吗？（穿整条链路发真请求，还是只看本地一跳？）

假绿比假红贵——漏判一个死进程，赔上的是它身后整条链路的夜班。
