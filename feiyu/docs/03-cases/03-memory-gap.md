# 案例三 · 17 小时记忆断档：日志全绿，功能全哑

## 问题

记忆写入静默失效了 17 小时。
日志里没有一个 `error`，监控没报警，服务状态正常——但她说不出前一天发生过什么。

## 定位过程

1. **找异常的不是日志，是数据**：缓冲里堆着消息，但没有任何 ingest 记录。
2. **三个原因叠在一起**：
   - 变量名被换掉了（新代码读 `MEMORY_GRAPH_*`，部署环境还是旧键）；
   - 请求缺了会话标识头；
   - 引擎的 logger 是个空函数——所有错误都被吞掉。
3. **修完之后还是不生效**：文件已经改对，但**进程里跑的是旧模块**；热加载没有替换掉已加载的代码，重启才生效。
4. **回灌**：按回合切分断档期的对话，剥离系统注入后再灌回去，避免把框架文本写进记忆。

## 结果

- 断档期数据补回；
- 修复后连续观察，记忆恢复写入；
- 日志里补上了真正的错误出口（logger 不再是空函数）。

## 教训

- **修完必须看"被消费的那一份"**：文件改对 ≠ 进程里对 ≠ 落盘对。
- **"有缓冲、无 ingest"** 是记忆系统最典型的断档信号；不要只看进程活着。
- **空实现的 logger 比没有日志更危险**：它让失败看起来像正常。
- **热加载不是重启**：改了只存在于内存/缓存的东西，必须验证生效版本。

## 可复用点

任何"写入型"子系统都该有这一条自检：**最近一次成功写入的时间戳**。
它不涨，就是断了——哪怕日志全绿、进程全活。
